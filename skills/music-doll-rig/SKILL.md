# MusicDoll 演奏者骨骼改造

## 这套东西解决什么

演奏者来自 MMD、Daz、Advanced Skeleton、Rigify、游戏拆包……命名、层级、朝向各不相同。演奏动画要求
所有角色的手臂 / 手指 / 腿满足同一套约定，否则同一组控制器参数换个角色表现就不一样。

**不能用固定脚本的原因**：认出哪根是哪根、判断现有层级好不好、决定要不要动，这些必须现场判断；
但判断清楚之后，改造动作本身是确定性的。所以形状是：**agent 分析 → 出一份改造单 → 脚本执行 → 脚本验收**。

## 什么时候别用它

- 控制器重的骨架（`Skirk` / `Skandrone` 这类，形变骨之间根本不互为父子链）——不要盲改，报给人；
- 一个文件里有多套骨架（英文命名版 / 日文 MMD 版 / Rigify 版）——先报给人选，脚本不自己挑；
- 只想看形态、不动文件 —— 用 `rig_analyze.py` / `rig_survey.py`，它们只读。

## 三条硬规则（改造的判据）

1. **Z 轴 = 弯起来时中间关节凸出去的那一侧**：手臂朝**正后方**、手指朝**这根手指自己的指甲平面法线**、
   腿朝**正后方**（膝盖拱形朝前，两者方向相反是正常的）。投影退化的骨跳过，不硬转。
2. **层级**：`上臂→前臂→手掌`、每根手指三节、`大腿→小腿→脚掌` 都要直接父子；夹在中间的扭转 / 辅助 /
   dummy 骨一律挂到主骨（MCH）下，不许插在链里。手指末端要有一根非形变"指尖骨"（长度取末节的 10%）。
3. **拱形 3%**：中间关节沿凸侧顶出弦长的 3%；弯对了不动、笔直就顶、弯反了先掰正再补。

> ⚠ 现状与上面这条有一处差异：`rig_apply` 现在对**已经有拱形**的链也是直接拉到正好 3%（实测把手臂的
> 3.13% 压到 3.00%、把腿的 0.88% 顶到 3.00%），并没有"弯对了就一点不动"。3% 与作者成品里的量级一致
> （`菲谢尔` 膝盖 3.2%、`Jeht` 4.6%），本例可以接受；但阶段 4 遇到膝盖本来就弯得厉害的模型要留意 ——
> 那会把好的拱形压平。要不要加"已经在 2% 以上且方向正确就不动"的分支，等作者定。

禁区：不删形变骨、不改 `use_deform`、不动顶点组与权重、不动物体层级、不动动画与状态数据。

## 工作流程

```
分析（rig_analyze，只读）
  → 改造单（JSON；rig_apply --dump-order 可导出草稿）
  → 执行（rig_apply，先 --dry-run 看一遍，再 --out 另存）
  → 验收（rig_verify，结构 / 功能 / 职责 三组断言）
  → 进度写回（rig_apply / rig_verify 自动写 `MusicDoll_Rig_Progress` 文本块）
```

执行顺序是**固定的**，不要调换：造主骨 → 改父子 → **造拱形** → **对齐尾端** → 改 roll → 加约束 → 整理集合。
拱形会挪动中间关节（实测 9 mm），尾端和 roll 都必须在它之后做，否则又对不齐 / 又偏掉。

## 脚本（同目录 `scripts/`）

| 文件 | 作用 |
|---|---|
| `rig_common.py` | 读骨架、算几何（骨轴 / 拱形 / 手链 / 手指链 / 前方向）、容错打开 .blend |
| `rig_roles.py` | 按名字判角色与变体（本体 / 影子 / MCH / 扭转 / 分段 / 末端） |
| `rig_survey.py` | 形态普查（只读），可传目录、文件或"一行一个路径"的 txt |
| `rig_analyze.py` | 认链 + 七项体检（层级 / Z / 拱形 / IK / 手掌复制 / 扭转 / 指尖骨） |
| `rig_apply.py` | 执行器：造主骨 / 改父子 / 拱形 / 尾端 / roll / 约束 / 集合 / 写进度 |
| `rig_verify.py` | 三组断言 + 逐顶点比 rest 网格（手臂 / 腿 / 手指都支持，腿部顶点单独统计）；结果写回进度块 |
| `rig_progress.py` | `MusicDoll_Rig_Progress` 文本块的读 / 写（单独可用） |
| `rig_pole_sweep.py` | 标定 `pole_angle`：扫角度、量中间关节朝凸侧 / 朝极向量的偏离（`--convex front` 给腿用） |
| `rig_arrows.py` | 生成 / 读取 / 删除指甲方向箭头（人工复核手指朝向用） |
| `reset_finger_tests.py` | 删掉手指的测试控制器（`T/I/M/R/P_<侧>_test`）并清掉引用它们的 IK，换口径重跑前用 |

```powershell
$blender = "D:\Program Files\Blender Foundation\Blender 5.0\blender.exe"
$skill   = "H:\music_doll_blender\skills\music-doll-rig\scripts"

# 只读分析
& $blender -b --factory-startup -P "$skill\rig_analyze.py" -- <file.blend> --armature <名字>

# 改造（先 dry-run，再另存）
& $blender -b --factory-startup -P "$skill\rig_apply.py" -- <file.blend> --armature <名字> `
    --auto-order --only arm.L --dry-run
& $blender -b --factory-startup -P "$skill\rig_apply.py" -- <file.blend> --armature <名字> `
    --auto-order --only arm.L --test-controllers --out <副本.blend>

# 标定 pole_angle（手臂）
& $blender -b --factory-startup -P "$skill\rig_pole_sweep.py" -- <副本.blend> `
    --owner MCH_ひじ.L --pole HP_L_test --targets "0.26,-0.10,0.98;0.30,-0.05,1.20" --range 0,190 --step 10

# 标定 pole_angle（腿：凸侧朝前，而且要对齐的角度在负值一侧，扫描范围必须含负数）
& $blender -b --factory-startup -P "$skill\rig_pole_sweep.py" -- <副本.blend> `
    --owner ひざ.L --root 足.L --pole FP_L_test --convex front `
    --targets "0.12,-0.37,0.31;0.06,-0.18,0.22" --range -180,15 --step 15

# 验收（不带 --chains 就是两臂 + 十指 + 两腿，共 14 条链；--save 才会把 DONE 落盘）
& $blender -b --factory-startup -P "$skill\rig_verify.py" -- <副本.blend> --armature <名字> `
    --reference <原件.blend> --save
```

## 手指：指甲方向的取法

规则要求每根手指的 Z 指向**这根手指自己的指甲方向**。取法（作者 2026-11-18 更正后的口径，已实现）：

- **四指**：用**食指根、小指根、手腕**三个点定手掌平面，取平面法线；**左右手符号相反**
  （同一个点序的叉积在镜像的右手上给的是另一侧，右手要取反号）。别再拿"现有 Z 的多数票"自动纠符号：
  那一手是在给错的原始朝向投票，投不出正确答案 —— 右手四指整根朝手背弯就是这么来的（作者看图发现）。
- **拇指**：用**肘、腕、拇指末端三点**定弯曲平面，取**平面内朝人物前方**的那一侧作为 Z 方向。
  拇指就在这个平面里弯，指甲朝前；T 型 / A 型姿态都适用。三点共线或前方几乎垂直于该平面时退回老办法
  （拇指链自身拱形凸侧、再退化就"手掌法线绕拇指轴转 90°、背离食指"）。
  > 复核过：`芙宁娜` 里作者的手工拇指 Z 与这条口径差 12°（和四指的 3~9° 同量级）；`Jeht` 那根差 46~64°，
  > 但 `Jeht` 的拇指本来就不在弯曲平面里（偏 50°），属于作者自己标注过的"手工残留"，不当模板。

别再用这些办法（都试过、都不稳）：面法线聚类（指尖是光滑圆头）、骨轴打射线量半径（会打到隔壁手指）、
末节顶点质心偏移（0.2~0.8 mm，被网格不对称淹没）、四个指根拟合平面（四点几乎共线，病态）。

**符号拿不准时，用渲染定案（`米提亚` 就是这么定的）**：沿手掌平面法线正反两侧各拍一张指尖特写
（正交、1200 px、Workbench + cavity），**有指甲的那一侧就是 nail 侧**。这一步比任何几何推断都硬：
`米提亚` 的原始 Z 左右不对称（左手四指朝手心、右手四指朝手背），而它的手指 rest 拱形凸侧也在**手心**那侧，
"现有 Z 多数票"和"拱形凸侧"两个办法在这里都会给出错误答案。

手型特殊、拱形不明显时用箭头兜底：`rig_arrows.py --create --side L` 摆出单箭头，人工转到指甲面，
再跑 `rig_apply`（**箭头优先**），复核完 `--clear`。

手指的 IK：挂在末节上、链长 3、极向量放指甲侧、`pole_angle` 也是 90°（与手臂同一个常数）。
指尖骨：已有的把 tail 改成"与前一根同向、长度 10%"，没有就补一根同规格的非形变骨
（注意 MMD 自带的"先"骨常常比末节还长，实测 143%~426%，必须缩）。

## 约束命名（接手时靠它认）

脚本加的所有约束一律 **`MD_<类型>_<链名>`**，`MD` = MusicDoll，链名与进度表的行名一致：

| 名字 | 挂在哪 | 内容 |
|---|---|---|
| `MD_IK_arm.L` | `MCH_ひじ.L`（无主骨时是前臂） | IK 链长 2，目标 `H_L_*`、极向量 `HP_L_*`、`pole_angle=90°` |
| `MD_Rot_arm.L` | 手掌 | 世界空间复制旋转 ← `H_L_*` |
| `MD_Twist_arm.L` | 每根扭转骨（同名各一条） | 局部 Y 复制旋转 ← 手掌骨，强度按位置递增 |
| `MD_IK_leg.L` | `MCH_ひざ.L`（或小腿） | IK 链长 2，目标 `F_L_*`、极向量 `FP_L_*`、`pole_angle=-90°` |
| `MD_Rot_leg.L` | 脚掌 | 世界空间复制旋转 ← `F_L_*` |
| `MD_IK_index.L` | 末节指骨 | IK 链长 3，目标 `I_L_*`、极向量 `I_L_pole_*`、`pole_angle=90°` |

`MD_` 开头 = 这套改造加的、可以重建；`mmd_*` / `mmd_tools_*` = 模型自带，**只 mute、不删**
（MMD 的扭转 `mmd_additional_rotation` 和 MMD 的腿 IK 都是这套处理）。

## 控制器的从属与摆位（2026-11-18 作者定，三条）

改造完不是"约束对上就完了"，控制器还得摆到**动画师真的会用**的位置。

1. **手指的目标控制器、手指极向量控制器，一律挂到同侧手腕控制器下面**
   （`I_L_test` / `I_L_pole_test` … → `H_L_test` 的子级）。
   好处是只动手腕这一个把手，整只手连着手指一起平移旋转，**手指之间的相对关系一根都不变**；
   不挂的话，动画师一动腕，五根手指的 IK 目标留在原地，手就被扯开了。
   `rig_apply.py` 默认就做这件事（不需要开关）。
2. **肘的极向量（`HP_*`）要往人身后挪一段**，不要压在肘关节上。
   压在关节上时极向量是退化的——它不告诉你往哪边掰；挪到身后它才真的开始工作。
   脚本里是 `--place-poles`，挪的距离取**上臂长 × 0.6**（本例 123 mm）。
3. **膝的极向量（`FP_*`）要往人身前挪一段**（这次取 200 mm，腿更长，压到 20 cm 以内）。

> 挪完极向量 `pole_angle` 必须重标：极向量压在关节上时那条角度是靠"没有极向量"凑出来的，
> 一挪开 IK 就真按极向量掰，rest 姿势会跟着变（实测胳膊位移 94 mm）。脚本会自动扫一遍，
> 判据是**中间关节朝极向量凸出去**，不是"回到原位"——位置两种解都满足，只有朝向分得清。
> 重标后胳膊回到 90°、残差约 1 mm；**腿这条不稳**：MMD 的 rest 腿本身是塌的、膝盖几乎压在弦上，
> 方向没有意义，扫出来的角度不可信（实测偏 88°）。腿这一段要人看一眼，别信脚本。

## 实测常数（截至 2026-11-17，三条链都扫过了）

| 链 | `pole_angle` | 依据 |
|---|---|---|
| 手臂 | **90°** | Z 对齐到正后方后，四个姿势下肘都正好指向极向量（偏离 0.02°） |
| 腿 | **-90°** | 扫 −180°~+15°：只有 −90° 这一档膝盖正好指向极向量（0.0°），两个目标位置都一样 |
| 手指 | **90°** | `Jeht` / `芙宁娜` 都是 90°；五指 `pole_angle` 一致 |

`pole_angle` 是相对骨骼自己的坐标系量的，所以**必须先把 Z 对齐再标定**：旧文件里的 0° / 180° 是
"Z 没对齐、把差值塞进角度里"的补偿，不要抄。扫描范围按链类不同 —— 手臂 0~180° 就够（超过 180° 解算
不再变化），**腿的对齐点在负值一侧（−90°）**，扫描必须含负数，否则会得出"没有一档对得上"的错误结论。

## 坑（都踩过）

1. **MMD 的 `mmd_additional_rotation` 要 mute**（只动这条链上的扭转骨）：它会把扭转按老骨朝向再施加一遍，
   和"手掌 Y 复制旋转"叠加。默认 mute，`--twist-action remove` 才是删。
2. **测试控制器要带着手掌的 rest 朝向**：手掌那条世界空间复制旋转会把骨骼直接拧到控制器朝向；
   控制器若是单位旋转，一加约束手掌就被拧走（rest 网格最大位移 0.22 m）。
3. **`use_stretch` 在这类骨架上实际不生效**（每根骨的 `ik_stretch` 都是 0，参考文件也这样）：
   超出链长的目标跟不住不是改造的错，功能验收要把控制器放在链长 0.85 倍以内。
4. **老模型的贴图可能缺失**：保存时 Blender 会报 `Unable to pack file`，但文件已经写出，不当失败。
5. **改骨的 rest 朝向不会动 rest 姿势的网格**（pose 为单位矩阵时形变恒等），但会改变"旋转怎么映射"——
   这正是对齐尾端 / 改 roll 的原理，别误以为会撕网格。
6. **中文路径**当命令行参数传没问题，PowerShell 里加引号；`.blend` 的 `open_mainfile` 可能因坏状态键抛异常，
   但文件其实已载入（`rig_common.open_mainfile_tolerant` 已处理）。
7. **MMD 的腿在 rest 姿势下是"塌"的，这是常态、不是文件坏了**：`ひざ` 这类腿骨的 rest 朝向并不沿着腿
   （实测把 MMD 的腿 IK 一 mute，脚踝跑到身后 46 cm、网格差 60 cm），模型打开时看到的样子是那条 IK
   摆出来的。所以：**必须先加我们的 IK 再禁用 MMD 的**，顺序反了（或中途存盘不保存约束）就会看到腿塌。
   加完我们的 IK 之后，网格会回到模型自己的 rest 形状 —— 与"原文件打开时的样子"差几厘米（本例 5.2 cm，
   1450 个腿部顶点），这是换掉 MMD 那条 IK 的必然结果，不是改造弄坏的。
8. **验"rest 网格不变"要把腿部顶点分出来看**：因为上一条，`rig_verify` 现在把受腿链（含 `D` / `_dummy_` /
   `_shadow_` 变体）影响的顶点单独统计（只作 INFO），其余顶点仍按 1e-5 的严格容差比。
   全部顶点塞进一个容差里，腿一改就必然红，那个断言也就没人看了。
9. **看"Z 是否等于算出来的指甲方向"是循环论证**：方向算错时那条断言照样通过（右手四指朝手背弯那次就是
   这么漏过去的）。所以 `rig_verify` 另有一条"右手目标 = 左手目标的镜像"（容差 10°，差 180° 就是符号没换向）。
   同理，拱形/屈指那两条检查比的是**指甲方向投影到垂直弦平面之后**的方向 —— 拇指的弦本身朝前，
   不投影会凭空多出 50 多度。特征是手指才发现的问题，验收器要照着能抓到的量来写。
10. **改造单里的指甲方向是"改骨架之前"算的，会过期**：手臂那条链造拱形时会把肘挪几毫米，拇指的弯曲平面
   （肘-腕-拇指末端）跟着转，照旧值对齐会差 2.8°（`米提亚` 实测）。`rig_apply` 现在按**当前几何**重算一次，
   偏了就换掉并报出来；有人转过箭头时仍以箭头为准。
11. **手指极向量要摆在"链根→指尖这条弦的指甲侧、垂直离开弦"的位置**（`rig_apply` 摆法是
   链根 + 弦×0.55 + 指甲垂直分量×0.8×弦长）。摆得贴着末节（离弦近、方向顺着手轴）时，各指的仰角不一样，
   同一个 `pole_angle=90°` 会让食指/无名指/小指斜着弯 —— `米提亚` 实测偏离指甲侧 32~43°，
   `rig_verify` 的"屈指朝指甲侧"（容差 30°）就是这么红的；改摆法后五指挥在 8.7° 以内。
12. **指甲侧到底在哪边，最终要靠指尖特写图定案**（`米提亚` 就是这么定的）：沿手掌平面法线的正反两侧
   各拍一张指尖特写（正交、1200 px、Workbench + cavity），有指甲的那一侧就是 nail 侧。
   这个模型的原始 Z 左右不对称（左手四指朝手心、右手四指朝手背，差 173° / 16°），
   "现有 Z 多数票"和"手指 rest 拱形"两个办法在这里都会给出错误答案（它的拱形凸侧在**手心**那侧）。
13. **给控制器改父级之前要先 `view_layer.update()`**：同一轮里刚造出来的空物体，`matrix_world` 还是单位阵，
   直接读出来再写回去，控制器会被搬到原点（实测右手的 `P_R_test` 掉到 (0,0,0)，网格位移 9.4 cm）。
   正确顺序是：update → 记下 `matrix_world` → 设 `parent` 与 `matrix_parent_inverse` → 写回 `matrix_world` → 再 update。

## 接手规矩（重要）

每个改造过的 `.blend` 里都有文本块 **`MusicDoll_Rig_Progress`**（`<<< AUTO:BEGIN >>>` 段由脚本重写，
表外 Notes 是人写的判断、脚本不动）：

- **没有这个块 = 完全没改造过**；
- 有、但 `status` 不是 `DONE` 的，按表接着干，**不要从头再来**；
- 表外 Notes 要当真（那是人留下的怀疑和待办）；
- `status` 变 `DONE` 要三件事同时成立：这一轮没有任何失败、这一轮把**十四条链都验过**、进度表里十四条
  都齐全。只跑了两臂的验收即使全过也**不会**标 DONE（那会把"没验过"写成"做完了"），输出里会列出
  "这一轮没验的链"；
- `rig_verify` 默认不存盘，`--save` 才会把 DONE 写进 .blend（旧模型的贴图缺失会让保存抛异常，脚本已按
  "文件其实写出来了"处理）。
