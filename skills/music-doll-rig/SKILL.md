# MusicDoll 演奏者骨骼改造

## 这套东西解决什么

演奏者来自 MMD、Daz、Advanced Skeleton、Rigify、游戏拆包……命名、层级、朝向各不相同。演奏动画要求
所有角色的手臂 / 手指 / 腿满足同一套约定，否则同一组控制器参数换个角色表现就不一样；
上半身怎么摆、头朝哪看也一样 —— 同一个人物必须给别人留下同样两个把手。

**不能用固定脚本的原因**：认出哪根是哪根、判断现有层级好不好、决定要不要动，这些必须现场判断；
但判断清楚之后，改造动作本身是确定性的。所以形状是：**agent 分析 → 出一份改造单 → 脚本执行 → 脚本验收**。

**环境**：实测于 Blender 5.0（Windows），脚本只用 `bpy` 标准 API，不依赖本机路径；命令行示例见「脚本」一节。

## 什么时候别用它

- 控制器重的骨架（`Skirk` / `Skandrone` 这类，形变骨之间根本不互为父子链）——不要盲改，报给人；
- 一个文件里有多套骨架（英文命名版 / 日文 MMD 版 / Rigify 版）——先报给人选，脚本不自己挑；
- 只想看形态、不动文件 —— 用 `rig_analyze.py` / `rig_survey.py`，它们只读。

## 第 0 步：单位与缩放（改骨骼之前先做，2026-11-25 作者定）

**这一条排在所有改造动作之前。** 场景单位设成 **0.01 米（1 个单位 = 1 厘米）**，骨骼与网格**各放大 100 倍并应用缩放**，
让两者的 `scale` 都是 1.0 —— 然后才开始认链、改骨骼。

为什么要这样：

- Blender 默认 1 个单位 = 1 米。MMD / 拆包来的模型导进来数字只有 0.0x 量级（`米娅-星彩` 身高 1.774 个单位），
  这串数字直接进 UE 就会按米解释成 1.7 厘米的小人；
- 放大 100 倍之后必须**应用**（`transform_apply`）：只把对象 scale 改成 100 而不应用，对象就带着 100 倍的缩放进 UE，
  骨架绑定 / 动画重定向都会跟着跑偏；应用之后缩放回到 1.0，厘米数字写进几何本身；
- 单位改成 0.01 米、几何放大 100 倍，两者正好抵消：角色真实尺寸不变（`米娅-星彩` 实测改前 1.7743 米 →
  改后 1.7743 米），数字变成厘米、对象缩放回到 1.0。

为什么必须在改骨骼之前：改完再整体放大，拱形、尾端、roll、IK 极向量的摆位（尤其腿的 500 mm）全都要按新尺度重算；
先放大，后面所有工作就都直接是厘米尺度，不用二次换算。

```powershell
# $blender / $skill 的取法见下面「脚本」那一节
& $blender -b --factory-startup -P "$skill\rig_units.py" -- <file.blend> --dry-run
& $blender -b --factory-startup -P "$skill\rig_units.py" -- <file.blend> --out <副本.blend>
```

`rig_units.py` 做的事：先记下解算后的网格顶点与骨骼头尾 → 把要放大的对象从父级上摘下来（保留世界位置）→
每个对象 `scale × 100` → `transform_apply(scale=True)` → 按原父子关系挂回 → 单位改成 0.01 米 → 再解算一遍逐顶点核对。

它自己的验收（跑完直接打印，任何一项不过就以非 0 退出）：

| 判据 | `米娅-星彩` 实测 |
|---|---|
| 对象缩放全部回到 1.0 | 骨骼 1.0 / 网格 1.0 |
| 逐顶点「新坐标 = 100 × 旧坐标」 | 48 550 点最大偏差 6.5e-05 个单位（0.65 μm） |
| 骨骼头尾「新位置 = 100 × 旧位置」 | 636 骨偏差 0 |
| 真实身高（米）不变 | 1.774323 → 1.774323 |

三个要记住的点：

1. **不要用「给父级应用缩放」代替**：对骨架应用缩放时 Blender 会连带子网格的数据一起处理，父子各放大一次就成了 10000 倍。
   脚本先把父子关系摘开、处理完再挂回去，就是为了避开这一条；
2. **处理过就别再跑**：脚本在场景自定义属性里记 `md_unit_scale` / `md_unit_factor`，重复跑会直接拒绝（`--force` 才强制）；
   同时写一个 `MusicDoll_Unit_Setup` 文本块，说明这个文件为什么坐标是厘米；
3. **导出侧配合**：FBX 导出保持 `Apply Unit` 打开（默认就是开）。实测把处理后的文件导出再导回 Blender，
   网格身高仍是 1.678 米 —— 单位元数据是对的，UE 按厘米读就是原尺寸。

## 五条硬规则（改造的判据）

1. **Z 轴 = 弯起来时中间关节凸出去的那一侧**：手臂朝**正后方**、手指朝**这根手指自己的指甲平面法线**、
   腿朝**正后方**（膝盖拱形朝前，两者方向相反是正常的）。投影退化的骨跳过，不硬转。
2. **层级**：`上臂→前臂→手掌`、每根手指三节、`大腿→小腿→脚掌` 都要直接父子；夹在中间的扭转 / 辅助 /
   dummy 骨一律挂到主骨（MCH）下，不许插在链里。手指末端要有一根非形变"指尖骨"（长度取末节的 10%）。
3. **拱形 3%**：中间关节沿凸侧顶出弦长的 3%；弯对了不动、笔直就顶、弯反了先掰正再补。

   > ⚠ 现状与这条有一处差异：`rig_apply` 现在对**已经有拱形**的链也是直接拉到正好 3%（实测把手臂的
   > 3.13% 压到 3.00%、把腿的 0.88% 顶到 3.00%），并没有"弯对了就一点不动"。3% 与作者成品里的量级一致
   > （`菲谢尔` 膝盖 3.2%、`Jeht` 4.6%），本例可以接受；但遇到膝盖本来就弯得厉害的模型要留意 ——
   > 那会把好的拱形压平。要不要加"已经在 2% 以上且方向正确就不动"的分支，等作者定。

4. **链条关节要对上并连上**：链上相邻两骨，后一根的 head 必须压在前一根的 tail 上，而且
   `use_connect = True`。对不上时改**前一根的 tail**（后一根的 head 才是关节位置，动它等于把整段肢体挪走）。
   每一条链的每一对关节都要满足：`上臂→前臂→手掌`、`大腿→小腿→脚掌`、每节手指（含指尖骨）。
   **脚掌→脚趾这一节也算在链里**（`脚关节要与脚趾关节连起来`），见下面那条专门说明。

   > **为什么非要连**：IK 是照着"关节链"解算的。尾端没接到下一根的头，中间关节一转两段之间就裂开；
   > 而 `use_connect = 0` 时子骨仍然能被**单独平移**——拖 IK 控制器，脚掌会从踝关节上掉下来、手掌会离开手腕。
   > MMD / PMX 换算来的骨架**必然**缺这一项：PMX 里骨的尾端只是一段偏移量（或"指向某根骨"），
   > 导进 Blender 之后 `use_connect` 全是 0。所以"看着没问题、一动就散"的模型，多半就是这里没做。

5. **改造过的链上，原件的约束一律 mute，只让自己加的 `MD_*` 生效**（2026-11-24 作者强调：这条忘掉就全乱）。

   MMD 原件在关节骨上挂着 `IK`、`mmd_additional_rotation`、`mmd_ik_limit_override`、
   `mmd_tools_at_dummy` 等；我们又要往同一根骨上加 IK 和复制旋转。两拨约束抢一根骨时，
   谁说了算取决于算的先后和空间设置 —— 表现就是"挪了极向量膝盖还往那边跑""改了尾端腿就歪"，
   调一天也调不明白。规矩很简单：**先把原件全静音，再让我们的约束单独说话**，现象立刻变得可预测。

   - 范围是"决定链姿势的骨"：上臂 / 前臂 / 手掌 / 大腿 / 小腿 / 脚掌 / 手指各节，以及它们的
     `_shadow_` / `_dummy_` 影子变体、MMD 的 IK 与角度限制。`rig_apply` 每跑一条链都会做这一步
     （`mute_legacy_constraints`），`rig_verify` 有断言「链上只留我们自己的约束」。
   - **例外**：`ひじ補助`、`肩C`、`腰キャンセル`、`目` 这类"跟着别人动"的辅助骨，它们的约束**没有替代品**，
     关掉会掉形变 —— 不在范围内，别顺手关。
   - 静音不删除：留着可回溯，接手的人能看出原件原来怎么接的。
   - **推论**：网格挂在哪条链上，我们的 IK / 复制旋转就要挂在哪条链上（MMD 常常把网格全挂给影子链
     `足D/ひざD/足首D`，本体链 `足/ひざ/足首` 一个权重都没有）。挂在没有权重的链上做了等于没做。

禁区：不删形变骨、不改 `use_deform`、不动顶点组与权重、不动物体层级、不动动画与状态数据。

## 工作流程

```
第 0 步：单位与缩放（rig_units，改骨骼之前先做，见上面那一节）
  → 分析（rig_analyze，只读）
  → 改造单（JSON；rig_apply --dump-order 可导出草稿）
  → 执行（rig_apply，先 --dry-run 看一遍，再 --out 另存）
  → 上半身 / 头部控制链（rig_upper，见下面专门那一节）
  → 验收（rig_verify，结构 / 功能 / 职责 三组断言；装了上部链就自动多验一条 upper）
  → 进度写回（rig_apply / rig_upper / rig_verify 自动写 `MusicDoll_Rig_Progress` 文本块）
```

执行顺序是**固定的**，不要调换：造主骨 → 改父子 → **造拱形** → **对齐尾端** → **连关节** → 改 roll → 加约束 → 整理集合。
拱形会挪动中间关节（实测 9 mm），尾端和 roll 都必须在它之后做，否则又对不齐 / 又偏掉。

上肢这条链要等四肢改完再加：它一加，胸 / 颈就由 IK 接管，网格的 rest 姿势也跟着归位
（本例是 0 位移，但换个体型就可能动几毫米）；先加它再改四肢，位移比对就说不清是谁引起的。

## 链条对接：尾端落在下一根的头 + connect（第四条硬规则）

判据只有两条，**同一条链的每一对关节都查**：

| 要满足 | 说明 |
|---|---|
| 后一根的 `head` = 前一根的 `tail` | 允许的差是 `rig_common.CHAIN_JOINT_TOLERANCE`（骨架单位 1e-3；MMD 换算来的模型 1 单位 = 1 cm，即 10 μm）。实测真正错开的是厘米级，机器精度那点零头不算错 |
| 后一根的 `use_connect = True` | 光对上不行：没连的子骨还能被单独平移，拖 IK 控制器时会真的散开 |

**对不上时改前一根的 tail**，不是改后一根的 head：

- head 是关节的坐标，改它等于把整段肢体（连同它下面的所有骨和权重）整体挪走；
- tail 只决定"这根骨有多长、朝哪指"，把它拽到下一个关节，链条就接上了 —— 代价是这根骨的 Y 轴变了
  （它的 Z/滚转映射跟着变，`.L` / `.R` 两侧都要重看），所以要报告出来、别偷偷改。

**哪些不能连**（判据是"这两根不是一个关节的两段"，不是"名字看着像"）：

- **分支骨**：手指第一节从手掌骨上长出来，不在 `手首` 的尾上；MMD 的 `つま先` 头在脚掌中段、
  不在 `足首` 的尾上（实测差 4.7 cm）。这类只报告、不连、更不许把父尾掰过去。
  （脚掌→脚趾这一节当然要连，但连的是"沿腿延伸"的那一根，见下面专门那一节。）
- **同一个头复制出来的两根**：MCH 主骨与它对应的形变骨 head 相同（不是 head→tail 的延续），
  连它会把形变骨的头拽到 MCH 的尾上去。有 MCH 时 IK 实际走 `MCH_上臂 → MCH_前臂 → 手掌`，连的是这一串。
- **扭转 / 辅助骨**：它们的尾端由 `align_aux_tails` 对到肘 / 腕，本来就不在链条关节上。

### 脚掌 → 脚趾：这一节必须连（额外的一条，2026-11-24 作者定）

**进 Unreal 之后，`足D → ひざD → 足首D → 足先EX` 是一条 LeftLeg 链，动画重定向（animation retarget）
就按这条链的顺序对骨；链上任何一节不连续，重定向出来的腿就是错的。** 所以在 Blender 里看着"这两根
没什么特殊关系"的脚掌与脚趾，其实必须是一节 —— 这也是最容易漏的一节，因为它不像肘 / 膝那样
一弯就能看出关节。

MMD 的腿经常同时长着两根脚趾骨。**哪一根算链条的下一节，看名字/角色，不看几何**（作者 2026-11-24 明确）：

| 骨 | 怎么认 | 怎么办 |
|---|---|---|
| `足先EX`（有的模型叫 `足先` / `toe` / `toe_end`） | 名字里带"足先"或"toe" | **是链条的下一节**：一定连。**它的头不在脚掌尾端时，把脚掌的尾端挪到它头上**（实测有模型它在脚掌中段、离脚掌尾 18 cm），再 `use_connect = 1` |
| `つま先` | 名字就是"つま先" | 脚掌中段长出去的分支：不连，也不许把脚掌的尾掰过去 |

也就是说：**迁就的方向是"脚的尾端 → 脚趾的头"**，不是反过来。脚掌的尾端本来只是 PMX 里的一段偏移量
（导入后常常就是一根朝上的桩），它不是关节位置；`足先EX` 的头才是关节。所以先确定 `足先EX` 的头在哪，
再把脚掌的尾端拉过去 —— 不要因为"脚趾的头离脚掌尾太远"就把它当分支放掉。

`rig_apply` / `rig_connect` / `rig_verify` / `rig_analyze` 都按这条挑：`足先EX` 型一律接进链里（差多少都挪尾端），
`つま先` 型只在这类脚趾骨不存在、并且自己正好落在脚掌尾端上时才当成延续。

**工具分工**：`rig_apply` 在拱形之后自动做（`fix_tails` 默认开），会把 `足先EX` 的头对上、把脚掌尾端拉过去再连；
已经绑好、只想补 connect 的半成品用 `rig_connect.py`（见下）；`rig_verify` 有两条独立断言 ——
「链条关节父子对接（tail=head + connect）」（腿那条会把脚趾算进去）和「影子腿链（UE 重定向用）」。

### 改尾端会动形变：影子链必须连，但驱动要一起重挂（2026-11-24 作者定规矩时发现的）

上面那条规矩在"骨架已经绑好、网格挂在本体骨上"的模型上无害，但**这个模型的网格全挂在影子链上**
（实测 `足D` 2066 / `ひざD` 1070 / `足首D` 673 / `足先EX` 267 个顶点，而 `足 / ひざ / 足首` 一个权重都没有）。
这种骨头的尾端不是装饰：

- MMD 把这些影子骨的姿势做成了 `mmd_additional_rotation`（`TRANSFORM`，**局部空间 ADD**，从 `_shadow_*` 借旋转）。
  这组数只在"影子骨与 `_shadow_*` 是同一个静置帧"时成立；
- 尾端一挪，静置帧变了，同一组局部旋转落到别的骨轴上 —— 实测**腿骨弯 50° 时脚飞出去 23 cm**
  （只挪脚掌那一节也有 23 cm，只挪三节里的两节有 21 cm）。

所以在**带权重的影子骨**上改尾端，必须同时把"姿势怎么来"换掉：把 `mmd_additional_rotation` 静音，
改成 **Copy Rotation（`owner_space = LOCAL`、`target_space = LOCAL_OWNER_ORIENT`、`mix_mode = REPLACE`、
目标 = 对应的本体骨）**。这个空间组合等于"把本体骨的局部旋转按本骨朝向共轭一次"，形变就只取决于本体骨、
与本骨朝哪儿无关 —— 实测改完逐顶点差 **≤ 2 µm**（rest 0.2 µm），屈膝 90° 也不变。

`rig_connect.py --fix-tails --reanchor-drive` 就是干这个的：

```bash
& $blender -b --factory-startup -P "$skill\rig_connect.py" -- <file.blend> --armature <名字> \
    --chains "左足D>左ひざD>左足首D>左足先EX;右足D>右ひざD>右足首D>右足先EX" \
    --fix-tails --reanchor-drive --save
```

它会顺着 `D 骨 → _shadow_* → _dummy_* → 父骨` 认出本体骨，再挂 `MD_Drive_*` 复制旋转。
只改尾端、不加 `--reanchor-drive`，`rig_verify` 的「影子腿链姿势来源」会直接报错并让你回来补这一步。

## 上半身 / 头部朝向控制链（第 6 步，2026-11-25 作者定）

四肢改完，人物还缺两个把手：**上半身怎么摆**、**头朝哪看**。这一步补上，形状照一份已经做完的成品文件
（对照用的参照是作者手上一个古筝版 `.blend`；你自己做的时候拿任一已完成这一步的文件当参照即可）：

```
  头骨（頭 / head） ──世界空间复制旋转──▶  Head_Control_test     ← 头的朝向直接等于它
                                                │
                                                ├── Track_To：本地 Z 轴指向 Look_At_test
                                                │                （头看着视点）
                                                │
                                                └── IK 的目标（链长 3）：
                                                    颈 → 上胸 → 胸            ← 上半身跟着这个点弯
                                                              ▲
                                                    极向量 = Look_At_test   （往视点那侧弯）
```

**这一套能干什么**：拖头部控制器，胸 / 颈跟着弯过去（上半身的朝向）；挪视点，头转向它
（头部的朝向）；两者正交，互不干扰。

### 四个决定，以及为什么

| 决定 | 理由 |
|---|---|
| IK 挂在**颈骨**上、链长 **3** | 链就是"颈 + 上胸 + 胸"（本例 `首 → 上半身2 → 上半身`）。**链头停在 `腰` 的上方那一节，不把腰包进来**：MMD 的 `腰` 下面挂着 `下半身`（腿），包进来一动腰就带着腿转 |
| 极向量 = **视点控制器** | 视点在人正前方，胸颈自然往前往下弯；这和"膝的极向量要放在身前"是同一个道理。少一个控件，且"看哪儿"和"往哪儿弯"天然一致 |
| 头骨用**世界空间**复制旋转（REPLACE） | 头直接等于控制器的朝向。用局部空间就会把颈的余数再叠一层，头会跟着脖子一起歪 |
| `pole_angle` **现场标定**，不写死 | 它相对骨自己的坐标系量，各骨架 roll 不同。见下面"标定的判据" |

### 两个控件都是独立的、没有父级（作者 2026-11-25 定）

本阶段只管把链搭对、把控件摆对：`Head_Control_test` / `Look_At_test` 都**不挂任何父级**，
也**不造** `Middle_Hand`（"双手中点"）那套跟随机制 —— 那是乐器阶段的事：
乐器模块自己会建 `Head_Control_<后缀>` / `Look_At_<后缀>`（古筝、钢琴、架子鼓模块都建，
`Look_At` 挂 `Middle_Hand`、`Middle_Hand` 用 driver 取左右手中点），
那时把这里的 test 引用换成它们、把位置对齐过来即可。

所以看到文件里同时存在 `Head_Control_test` 与 `Head_Control_Mia`（一个在头部、一个停在原点）
**不是 bug**：后者是乐器阶段建的，等着被对齐。`music-doll-instrument-controls` 的第 6 步会把模块
控件对齐到这对 test、把 `MD_IK_upper` / `MD_Rot_upper` 的目标换成模块控件、再删掉 test 那对；
老文件（本阶段没搭过链）则是它按同一套规矩从零补 —— 两边判据一致，不要各改一套。

### 标定的判据：rest 关节位移最小

把头部控制器摆在链条末端（= 颈的尾端 = 头骨的 joint）不动，扫 `pole_angle` 一圈，
取**"rest 关节位形被解回来的误差最小"**的那一档。道理很直接：目标就压在链的末端，
rest 姿势本身就是 IK 的一个解；只有极向量平面与骨自身的弯曲平面重合时，解算才不会把 rest 掰歪。

实测（`米娅-星彩`，链长 0.4330）：0° 差 23.5 mm、45° 差 12.8 mm、**90° 差 0.000 mm**、180° 差 23.5 mm ——
V 形谷很干净，1° 精度足够。**90° 与作者成品的取值一致**（他那份是手工摆的，两处独立得到同一个数）。

> 标完还要复核"往极向量那侧弯"：把头部控制器往前推 15% 链长，量中间关节相对"链根→末端"这条弦
> 的垂直偏移，与极向量相对同一根弦的垂直偏移的夹角。这一条和手臂 / 腿的极向量判据是同一套口径，
> 目的是抓"角度标对了但平面反了"这种解。（本例四档姿势都是 0.0°。）

### 有效范围：只能收，不能伸

rest 姿势下链条已经接近**绷直**（三节骨长之和 0.4373、链根到末端 0.4330，只有 4.3 mm 余量），
所以头部控制器**往外 / 往上拽是拽不动的**（目标超出链长，`ik_stretch` 在这些骨上都是 0，
和四肢的 `use_stretch` 一样不生效）：

- 能做的：把头往下 / 往前 / 往侧压 —— 上半身跟着弯，这是演奏时最常用的动作；
- 不能做的：把头顶高、把上身往上拔。要"挺直一点"就动 `センター` / `上半身`，
  别指望这个控件。

### 与作者成品的两处有意差异

1. **三对关节都接上了**（`上半身→上半身2`、`上半身2→首`、`首→頭`，都 `use_connect=1`）。
   作者那份成品是 `connect=0`；按第四条硬规则，IK 链上的子骨不连就能被单独平移，
   拖控制器时链条会散，所以我们接上。这三对关节本来就逐对重合（gap=0），接上前后的 rest 网格
   逐顶点差 **0.000000000 m** —— 接上只锁住平移，不动任何形变。
2. **头部控制器摆的位置不同**：作者那份在颈尾前方约 7 cm（近似"头心"，他的口味）；
   我们摆在**颈尾上** —— 这样 rest 姿势是这条链的精确解，rest 网格位移为 **0**，
   而`Head_Control_test` 同时就是"头绕哪里转"的轴心。

### 不顺手静音影子双胞胎

四肢那条规矩是"链上只让自己的约束生效，影子骨一起静音"。躯干**不这么做**：
`_shadow_上半身` 这类骨是别人的"姿势来源"（别的骨从它们身上借旋转），静音它们会把
不相干的东西弄掉。这里只静音**链上这几根骨自己**的 `mmd_*` / IK 约束，并且在报告里点出
"这些骨还有影子双胞胎" —— 如果网格挂在影子躯干骨上，那形变不归这条链管，要人来判断。

## 手指：指甲方向的取法

规则要求每根手指的 Z 指向**这根手指自己的指甲方向**。取法（作者 2026-11-18 更正后的口径，已实现）：

- **四指**：用**食指根、小指根、手腕**三个点定手掌平面，取平面法线；**左右手符号相反**
  （同一个点序的叉积在镜像的右手上给的是另一侧，右手要取反号）。别再拿"现有 Z 的多数票"自动纠符号：
  那一手是在给错的原始朝向投票，投不出正确答案 —— 右手四指整根朝手背弯就是这么来的（作者看图发现）。
- **拇指**：用**肘、腕、拇指末端三点**定弯曲平面，取**平面内朝人物前方**的那一侧作为 Z 方向。
  拇指就在这个平面里弯，指甲朝前；T 型 / A 型姿态都适用。三点共线或前方几乎垂直于该平面时退回老办法
  （拇指链自身拱形凸侧、再退化就"手掌法线绕拇指轴转 90°、背离食指"）。
  > 复核过：`芙宁娜` 里作者的手工拇指 Z 与这条口径差 12°（和四指的 3~9° 同量级）；`Jeht` 那根差 46~64°，
  > 但 `Jeht` 的拇指本来就不在弯曲平面里（偏 50°），属于作者自己标注过的"手工残留"，不当模板。

别再用这些办法（都试过、都不稳）：面法线聚类（指尖是光滑圆头）、骨轴打射线量半径（会打到隔壁手指）、
末节顶点质心偏移（0.2~0.8 mm，被网格不对称淹没）、四个指根拟合平面（四点几乎共线，病态）。

**符号拿不准时，用渲染定案（`米提亚` 就是这么定的）**：沿手掌平面法线正反两侧各拍一张指尖特写
（正交、1200 px、Workbench + cavity），**有指甲的那一侧就是 nail 侧**。这一步比任何几何推断都硬：
`米提亚` 的原始 Z 左右不对称（左手四指朝手心、右手四指朝手背），而它的手指 rest 拱形凸侧也在**手心**那侧，
"现有 Z 多数票"和"拱形凸侧"两个办法在这里都会给出错误答案。

手型特殊、拱形不明显时用箭头兜底：`rig_arrows.py --create --side L` 摆出单箭头，人工转到指甲面，
再跑 `rig_apply`（**箭头优先**），复核完 `--clear`。

手指的 IK：挂在末节上、链长 3、极向量放指甲侧、`pole_angle` 也是 90°（与手臂同一个常数）。
指尖骨：已有的把 tail 改成"与前一根同向、长度 10%"，没有就补一根同规格的非形变骨
（注意 MMD 自带的"先"骨常常比末节还长，实测 143%~426%，必须缩）。

## 控制器的从属与摆位（2026-11-18 作者定，三条）

改造完不是"约束对上就完了"，控制器还得摆到**动画师真的会用**的位置。

1. **手指的目标控制器、手指极向量控制器，一律挂到同侧手腕控制器下面**
   （`I_L_test` / `I_L_pole_test` … → `H_L_test` 的子级）。
   好处是只动手腕这一个把手，整只手连着手指一起平移旋转，**手指之间的相对关系一根都不变**；
   不挂的话，动画师一动腕，五根手指的 IK 目标留在原地，手就被扯开了。
   `rig_apply.py` 默认就做这件事（不需要开关）。
2. **肘的极向量（`HP_*`）要往人身后挪一段**，不要压在肘关节上。
   压在关节上时极向量是退化的——它不告诉你往哪边掰；挪到身后它才真的开始工作。
   脚本里是 `--place-poles`，挪的距离取**上臂长 × 0.6**（本例 123 mm）。
3. **膝的极向量（`FP_*`）要往人身前挪……而且得挪够远**：**500 mm**（2026-11-24 更正，原来写 200 mm）。

   膝盖朝哪一边，是由"极向量落在弦的哪一侧"决定的。极向量只放 200 mm 时，脚往前抬过 400 mm
   它就被甩到弦的后面去了，膝盖立刻翻到身后（实测在 `米娅-星彩` 上：脚前移 100/200/300 mm 膝盖朝前，
   400 mm 起朝后，抬腿动作直接反关节）。放到 500 mm 时脚前移 600 mm 以内膝盖都朝前。
   `rig_apply` 现在按 500 mm 摆；手改过的老文件要自己复查这一项，看"把脚抬高，膝盖有没有翻"。

> 挪完极向量 `pole_angle` 必须重标：极向量压在关节上时那条角度是靠"没有极向量"凑出来的，
> 一挪开 IK 就真按极向量掰，rest 姿势会跟着变（实测胳膊位移 94 mm）。脚本会自动扫一遍，
> 判据是**中间关节朝极向量凸出去**，不是"回到原位"——位置两种解都满足，只有朝向分得清。
> 重标后胳膊回到 90°、残差约 1 mm；**腿这条不稳**：MMD 的 rest 腿本身是塌的、膝盖几乎压在弦上，
> 方向没有意义，扫出来的角度不可信（实测偏 88°）。腿这一段要人看一眼，别信脚本。

## 父子关系：只能"无逆"地挂（2026-11-28 作者定，跨引擎唯一的硬约束）

**给控件改父级，只能走"无逆"那一种。** 判据只有一条：改完 `matrix_parent_inverse` 必须是单位阵。

为什么：Blender 算世界位置用的是

    世界 = 父级世界 × matrix_parent_inverse × 本地（location / rotation / scale）

`Ctrl+P` → Object (Keep Transform)，以及任何"设 `parent` 再把 `matrix_parent_inverse` 写成
父级世界矩阵的逆"的代码，都让前两项互相抵消 —— 于是 **location / rotation 里存下来的其实是世界值**。
Blender 自己怎么算都自洽（抵消掉了），所以文件里看着一点毛病都没有；
可导出器（`.harpist` / `.drummer` / `.animation` / 控制器 FBX）只写 location / rotation，
引擎按"父级 × 本地"重建，世界值被当成局部值又乘了一遍父级 —— 部件就飞到别处去了。
实测：父级是转 98° 的手腕时偏 1.18 m；父级带 99 倍缩放时偏 11 km。**只有跨引擎才暴露。**

- **UI 里**：先 `Alt+P`（这里"保持变换"是对的，把子物体摘下来）→ 再 `Ctrl+P` → **Object**
  （不要选 "Object (Keep Transform)"）。
- **脚本里**：

  ```python
  bpy.context.view_layer.update()
  world = obj.matrix_world.copy()
  obj.parent = parent
  obj.matrix_parent_inverse.identity()   # ← 区别只有这一行
  obj.matrix_world = world               # basis 于是等于 父级⁻¹ × 世界，是真正的局部值
  bpy.context.view_layer.update()
  ```

  **不要**写 `obj.matrix_parent_inverse = parent.matrix_world.inverted()` —— 那正好是要避免的那一种。

两条自查断言（`check_parent_inverse.py` 一次跑完，退出码非 0 就是有雷）：

1. 任何父级不是单位变换的物体，`matrix_parent_inverse` 必须是单位阵 —— 否则它记录的"局部值"是假的；
2. 反向验收：拿基准值做 `父级世界 × 本地`，算出的落点必须等于场景里的实际位置；
   跨引擎再算一遍（×100、Y 轴取反、四元数取共轭之后），两边必须落在同一点。

踩过 / 会踩的地方（前两处是 2026-11-28 改掉的，后两处靠这条规矩防）：

| 位置 | 场景 | 父级带什么 |
|---|---|---|
| `rig_apply.py` 手指控制器挂手腕（实测中招） | `I_L_test` / `I_L_pole_test` → `H_L_test` | 手腕 rest 朝向（米娅 98.4°） |
| `rig_units.py` 缩放后挂回父级 | 网格 / 骨架挂回演奏者根 | 成人骨架通常是单位阵，换个父级带旋转的绑定就会中 |
| `install_instrument_controls.py` 补控件 / 换父级 | 吉他补的 `F_*`、test 父级换成实际控件 | 同上 |
| 手工或工具里把控件挂到乐器支点 | 竖琴 `Head` → `harp_pivot`（95°） | 支点倾角（芭芭拉那次的现场） |

**已经中过招的文件怎么修**：把子物体 `Alt+P`（保持变换）摘下来 → `Ctrl+P` 不带 inverse 挂回去 →
**重新录一遍所有基准姿势**（旧基准是按"世界值冒充局部值"记的，不重录等于没修）。
实测修完画面不动（世界矩阵差 1.3e-7 m），而写进文件的数字从"世界值"变成"父级⁻¹ × 世界"。

文件多的时候别手工点：`check_parent_inverse.py` 扫一遍看清楚 → `fix_parent_inverse.py --dry-run` 看它要动谁 →
正式跑（默认按相对路径备份到文件旁边的 `_parent_fix_backup/`，加 `--backup-dir` 可以挪走）。
脚本是把 `basis` 换成 `PI × basis`，所以父级带非均匀缩放、分解不出无剪切矩阵的会自己跳过并报告。
带关键帧动画的物体默认不碰（关键帧还停在旧空间），要一起换算得加 `--animate`——换算后关键帧之间
会有毫米级插值差，重要动画建议在原流程里重烘，别指望这一步无损。

## 实测常数（截至 2026-11-17，三条链都扫过了）

| 链 | `pole_angle` | 依据 |
|---|---|---|
| 手臂 | **90°** | Z 对齐到正后方后，四个姿势下肘都正好指向极向量（偏离 0.02°） |
| 腿 | **-90°** | 扫 −180°~+15°：只有 −90° 这一档膝盖正好指向极向量（0.0°），两个目标位置都一样 |
| 手指 | **90°** | `Jeht` / `芙宁娜` 都是 90°；五指 `pole_angle` 一致 |

`pole_angle` 是相对骨骼自己的坐标系量的，所以**必须先把 Z 对齐再标定**：旧文件里的 0° / 180° 是
"Z 没对齐、把差值塞进角度里"的补偿，不要抄。扫描范围按链类不同 —— 手臂 0~180° 就够（超过 180° 解算
不再变化），**腿的对齐点在负值一侧（−90°）**，扫描必须含负数，否则会得出"没有一档对得上"的错误结论。

## 坑（都踩过）

1. **MMD 的 `mmd_additional_rotation` 要 mute**（只动这条链上的扭转骨）：它会把扭转按老骨朝向再施加一遍，
   和"手掌 Y 复制旋转"叠加。默认 mute，`--twist-action remove` 才是删。
2. **测试控制器要带着手掌的 rest 朝向**：手掌那条世界空间复制旋转会把骨骼直接拧到控制器朝向；
   控制器若是单位旋转，一加约束手掌就被拧走（rest 网格最大位移 0.22 m）。
3. **`use_stretch` 在这类骨架上实际不生效**（每根骨的 `ik_stretch` 都是 0，参考文件也这样）：
   超出链长的目标跟不住不是改造的错，功能验收要把控制器放在链长 0.85 倍以内。
4. **老模型的贴图可能缺失**：保存时 Blender 会报 `Unable to pack file`，但文件已经写出，不当失败。
5. **改骨的 rest 朝向不会动 rest 姿势的网格**（pose 为单位矩阵时形变恒等），但会改变"旋转怎么映射"——
   这正是对齐尾端 / 改 roll 的原理，别误以为会撕网格。
6. **中文路径**当命令行参数传没问题，PowerShell 里加引号；`.blend` 的 `open_mainfile` 可能因坏状态键抛异常，
   但文件其实已载入（`rig_common.open_mainfile_tolerant` 已处理）。
7. **MMD 的腿在 rest 姿势下是"塌"的，这是常态、不是文件坏了**：`ひざ` 这类腿骨的 rest 朝向并不沿着腿
   （实测把 MMD 的腿 IK 一 mute，脚踝跑到身后 46 cm、网格差 60 cm），模型打开时看到的样子是那条 IK
   摆出来的。所以：**必须先加我们的 IK 再禁用 MMD 的**，顺序反了（或中途存盘不保存约束）就会看到腿塌。
   加完我们的 IK 之后，网格会回到模型自己的 rest 形状 —— 与"原文件打开时的样子"差几厘米（本例 5.2 cm，
   1450 个腿部顶点），这是换掉 MMD 那条 IK 的必然结果，不是改造弄坏的。
8. **验"rest 网格不变"要把腿部顶点分出来看**：因为上一条，`rig_verify` 现在把受腿链（含 `D` / `_dummy_` /
   `_shadow_` 变体）影响的顶点单独统计（只作 INFO），其余顶点仍按 1e-5 的严格容差比。
   全部顶点塞进一个容差里，腿一改就必然红，那个断言也就没人看了。
9. **看"Z 是否等于算出来的指甲方向"是循环论证**：方向算错时那条断言照样通过（右手四指朝手背弯那次就是
   这么漏过去的）。所以 `rig_verify` 另有一条"右手目标 = 左手目标的镜像"（容差 10°，差 180° 就是符号没换向）。
   同理，拱形/屈指那两条检查比的是**指甲方向投影到垂直弦平面之后**的方向 —— 拇指的弦本身朝前，
   不投影会凭空多出 50 多度。特征是手指才发现的问题，验收器要照着能抓到的量来写。
10. **改造单里的指甲方向是"改骨架之前"算的，会过期**：手臂那条链造拱形时会把肘挪几毫米，拇指的弯曲平面
   （肘-腕-拇指末端）跟着转，照旧值对齐会差 2.8°（`米提亚` 实测）。`rig_apply` 现在按**当前几何**重算一次，
   偏了就换掉并报出来；有人转过箭头时仍以箭头为准。
11. **手指极向量要摆在"链根→指尖这条弦的指甲侧、垂直离开弦"的位置**（`rig_apply` 摆法是
   链根 + 弦×0.55 + 指甲垂直分量×0.8×弦长）。摆得贴着末节（离弦近、方向顺着手轴）时，各指的仰角不一样，
   同一个 `pole_angle=90°` 会让食指/无名指/小指斜着弯 —— `米提亚` 实测偏离指甲侧 32~43°，
   `rig_verify` 的"屈指朝指甲侧"（容差 30°）就是这么红的；改摆法后五指挥在 8.7° 以内。
12. **指甲侧到底在哪边，最终要靠指尖特写图定案**（`米提亚` 就是这么定的）：沿手掌平面法线的正反两侧
   各拍一张指尖特写（正交、1200 px、Workbench + cavity），有指甲的那一侧就是 nail 侧。
   这个模型的原始 Z 左右不对称（左手四指朝手心、右手四指朝手背，差 173° / 16°），
   "现有 Z 多数票"和"手指 rest 拱形"两个办法在这里都会给出错误答案（它的拱形凸侧在**手心**那侧）。
13. **给控制器改父级之前要先 `view_layer.update()`**：同一轮里刚造出来的空物体，`matrix_world` 还是单位阵，
    直接读出来再写回去，控制器会被搬到原点（实测右手的 `P_R_test` 掉到 (0,0,0)，网格位移 9.4 cm）。
    正确顺序是：update → 记下 `matrix_world` → 设 `parent`、**把 `matrix_parent_inverse` 归零** → 写回
    `matrix_world` → 再 update。归零那一步不能省：写成"设 parent 与 `matrix_parent_inverse`（=父级世界矩阵的逆）"
    就是把世界值烙进 location，Blender 里看不出、导出到 Unreal 才炸（见「父子关系：只能无逆地挂」那一节）。
14. **`use_connect = True` 会把子骨的头吸到父骨的尾上**（Blender 的行为：连上就锁定头的位置）。所以顺序必须是
   "先把父尾对到子头，再连"；反过来先把子骨的头挪过去，整段肢体就跟着挪了。差值在阈值内时也会被吸一点点
   （`瓦列里` 实测 13 根骨的头被吸走 ≤1.6e-5，网格最大位移 3.8e-5 —— 等于没动，可以不管）。
15. **"不重合就把 tail 掰过去"之前，先确认这两根真的是一个关节的两段**：`瓦列里` 的 `足首` 尾端现在指向
   `足先EX` 的头，而 PMX 原始文件里它指向 `つま先` 的头（两者差 4.7 cm）—— 这不是谁改坏了，是作者为了让
   Unreal 的 LeftLeg 重定向链（`足D→ひざD→足首D→足先EX`）连续，**特意**把尾端挪到了 `足先EX` 上，
   而 `つま先` 留在脚掌中段当分支。照"不重合就掰"硬掰回去，重定向链就断了。
16. **MMD 骨架的 IK 常常不在"本体链"上**：`足D / ひざD / 足首D` 这条影子链才是 `IK` 约束实际驱动的那串，
   而分析器默认只认本体链（`足 / ひざ / 足首`，变体 plain）。两条链的关节都要连，`rig_connect --chains`
   得把影子链自己写出来，而且多半要 `--fix-tails --reanchor-drive`（影子骨的尾端都是朝上的桩，
   而带权重的影子骨一掰尾端就会动形变，见"脚掌→脚趾"那一节）；别看到分析器报"关节对接 ok"就以为
   整条腿都连好了。`rig_verify` 现在对影子腿链有两条独立断言，漏了会直接红。
17. **认躯干链时不能用 `is` 比父子关系**：bpy 每次访问都给出新的 Python 包装对象，
   `child.parent is parent_bone` 永远是 False —— 表现就是"头骨找到了、但不在颈骨下面"（第一版认链就
   栽在这里，直接认不出链）。要比名字。
18. **`chain_joint_report` 要求链名"根在前、尖在后"**：IK 链在代码里的顺序是"颈 → 根"（从属关系自下而上），
   直接喂给关节检查会把 `首→頭` 当成父→子，报出 gap=0.27 的假失败。验收时用
   `list(reversed(chain)) + [头骨]`。
19. **`use_connect` 写在子骨上**：`上半身.connect` 永远是 0（它是链根，父级是腰），要连的是
   `上半身2 / 首 / 頭` 这三根。看报告时别把"链根没连"当成漏做。
20. **躯干的影子双胞胎不要顺手静音**：四肢那条规矩是"链上只留自己的约束"，但那是因为四肢的影子骨
   就是链上的成员（网格挂在它们身上）。躯干的 `_shadow_上半身` 是"姿势来源"，静音它会把不相干的骨
   弄掉形变 —— `rig_upper` 只静音链上这几根骨自己的约束。
21. **`Look_At` 同时是极向量**：把它挪到人身后（或远远高出头顶），胸颈就会往那边弯。这不是 bug，
   是"视点即弯曲方向"的直接后果；要"看着身后"又不想胸往后仰，只能另加一个独立极向量（本阶段没做）。
22. **本阶段两个控件都不挂父级**（作者 2026-11-25 定）：不要"顺手"把它们挂到 `controller_root` 或
   `Middle_Hand` 下面 —— 后面的乐器阶段会把 test 控件换成模块自己的对象，挂错父级会让替换后的位置对不上。

## 接手规矩（重要）

每个改造过的 `.blend` 里都有文本块 **`MusicDoll_Rig_Progress`**（`<<< AUTO:BEGIN >>>` 段由脚本重写，
表外 Notes 是人写的判断、脚本不动）：

- **没有这个块 = 完全没改造过**；
- 有、但 `status` 不是 `DONE` 的，按表接着干，**不要从头再来**；
- 表外 Notes 要当真（那是人留下的怀疑和待办）；
- `status` 变 `DONE` 要三件事同时成立：这一轮没有任何失败、这一轮把**十四条链都验过**、进度表里十四条
  都齐全。只跑了两臂的验收即使全过也**不会**标 DONE（那会把"没验过"写成"做完了"），输出里会列出
  "这一轮没验的链"；
- **进度表里还有第 15 行 `upper`**（上半身 / 头部控制链）。装了这条链（文件里有 `MD_IK_upper`）的文件，
  验收时它会自动加进这一轮，"齐全"的口径变成"十四条 + upper"：没验过它、或它红着，`status` 都不会是
  DONE。没装这条链的老文件不受影响。`rig_upper.py` 加完链会把 `status` 主动退回 `IN PROGRESS` ——
  加完不等于验过；
- `rig_verify` 默认不存盘，`--save` 才会把 DONE 写进 .blend（旧模型的贴图缺失会让保存抛异常，脚本已按
  "文件其实写出来了"处理）。
- **"链条关节对接"这条断言是 2026-11-24 才加的**：在那之前改造完、标了 DONE 的文件验不过它（关节本来就
  没连）。补一次 `rig_connect.py --save` 就行，**不用重跑 `rig_apply`** —— 关节位置早就对上了，缺的只是
  那个开关；重跑 apply 会重做拱形 / roll，反而把已经验收过的东西又动一遍。
- **上半身 / 头部这条链的状态用 `rig_upper.py --dry-run` 看**：它会把"认出来的链、每根骨上挂的约束
  （含静音状态）、两个控件在哪 / 有没有父级、同名族里还有谁"一次摊开，不写任何东西。
  表里没有 `upper` 行就当没装过；有、但 `status` 又不是 DONE，说明加了没验，跑一次全量 `rig_verify` 即可。
